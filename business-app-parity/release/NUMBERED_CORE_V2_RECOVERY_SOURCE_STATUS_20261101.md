## What is now implemented and tested
- **Offline, source-only** `shared/lib/numbered-records-v2-preflight.mjs` defines a strict versioned core numbered-records snapshot contract. Every one of the 20 ordinary base-app record tables **and** 3 permanent-number identity tables is mandatory; unknown tables are refused until explicitly modeled. A complete per-table row-count manifest, no truncation, serialized values, immutable Customer # / Job # serial mappings and original SQLite AUTOINCREMENT high-water are mandatory.
- The ordinary D1 record relationship, financial-refund, deposit-audit and signed-agreement validators are reused. It rejects orphan records, invalid refund ledger entries, duplicate payment provider identifiers, incomplete or cross-customer Job # maps, and any unverified high-water history. It never computes new identities from row position or customer dates.
- `planNumberedCoreRecordsV2Restore` is a **pure no-write planner**, not an implementation of restore. It refuses any differing saved row with the same immutable primary key, any reused consumed serial, and — critically — validates the **merged** payment/refund/audit/customer ledger. Two individually safe archives can become unsafe when combined: separate succeeded refunds might over-reserve the original payment, or separate payment rows may reuse one Stripe checkout reference. These conditions fail closed.
- `shared/scripts/test-numbered-records-v2-preflight.mjs` runs **54 actual offline checks**, including a local in-memory SQLite replay demonstrating that the next Customer # and Job # follow historical high-water marks, not current MAX().
- `shared/scripts/test-numbered-v2-schema-coverage.mjs` runs **7 source coverage checks**. The owner-verified QA baseline has exactly **25 SQL migrations**, creating **20 business-record tables** plus the ephemeral `auth_rate_limits` operational table. `d1_migrations` is migration-journal metadata outside source CREATE TABLE statements. The separately proposed immutable numbering SQL creates exactly 3 more durable tables. Future additional persistent tables cause a CI failure until reviewed and included in the archive. Source coverage is **not** proof of any currently deployed schema.
- Independent GitHub Actions workflow `.github/workflows/fire-numbered-core-recovery-v2-preflight.yml` runs these tests with no provider or remote D1 access; the tests also run upon changes to relevant source schema migrations.

## Additional Nov 1 implementation: reusable atomic disposable restore
- `shared/lib/disposable-numbered-v2-restore.mjs` now contains a reusable **atomic** restore routine instead of leaving the replay algorithm only inside a test. It is intentionally not wired to any Worker/API route and refuses physical/on-disk SQLite, externally attached databases, nonempty durable tables, unknown future schemas, unexpected or missing original SQL columns, bad/missing immutable-number triggers, invalid foreign key setup, existing serial state, or invalid/unverified numbered core archives.
- Every one of the current 20 ordinary QA business-record tables and 3 proposed permanent identity tables is restored inside one disposable `:memory:` SQLite transaction. Source values (including refund/payment ledger entries and all real SQL columns) are read back and compared **before COMMIT**, SQLite foreign keys and integrity are checked, and the original historical SQLite AUTOINCREMENT high-water is verified. On interruption or error the transaction is rolled back.
- The physical `test-numbered-v2-atomic-sqlite-rehearsal.mjs` was changed to exercise the **actual reusable routine**, not merely a separately hand-written test insertion. It also proves an external attached database, unreviewed extra durable table, missing anti-renumber trigger, preexisting data, and actual **on-disk file database** are rejected. The temporary physical test file is removed. No owner personal files, connected providers or database records are used.
- **Hard safety boundary:** even though this routine performs a real in-memory restore, it is *not a complete app backup/restore product*, a private recovery rehearsal, an HTTP v2 backup endpoint, or approval to migrate/enable numbers. Device-local IndexedDB photo bytes, Cloudflare R2 contents, optional property/service-location feature tables, credentials, production provider configuration, actual migration lineages and durable off-device archive custody remain outstanding. Do not remove v1 HTTP409 guard, deploy the routine, or claim Gate10 acceptance.
