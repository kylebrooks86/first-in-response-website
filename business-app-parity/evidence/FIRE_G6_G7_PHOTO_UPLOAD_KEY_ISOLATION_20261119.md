# FIRE Business App — G6/G7 photo write/read/delete identity safeguards — 2026-11-19

**Scope:** Existing main-based, unmerged and undeployed DRAFT PR #270, branch `work/fire-main-qa-dr-live-unified-source-20261114`. Only source, synthetic regression tests and GitHub CI; no owner records/images/provider access.

## Concrete production defects corrected

1. `shared/app/api/customer-photos/route.ts` previously allowed an uploaded File with zero bytes and unbounded caption/original filename metadata into the photo-save path. This could create a worthless stored object and misleading permanent customer record. File bytes must now be nonempty; caption remains compatible with the existing offline QA-master **2,000-character** limit and filename with its **240-character** limit. Invalid metadata is refused **before customer D1 lookup, bucket put or metadata insert**. This is in addition to existing MIME, actual streamed multipart-byte cap, owner authentication, browser-origin and D1 lost-ACK safety. No change to approved full-resolution photo formats/sizes or storage service selection.

2. `shared/app/api/customer-photos/[id]/route.ts` previously trusted the D1 `object_key` for GET and DELETE without independently verifying that the object key belonged to the **same saved customer ID and photo ID**. Malformed/cross-customer metadata might retrieve unrelated bytes or delete another customer's only stored original. Both handlers now require `customers/<customer_id>/<photo_id>.<extension>` with 128-character ID limits aligned to `shared/lib/photo-storage-integrity.ts`, and refuse mismatches with no R2 byte operation or D1 mutation. Existing same-origin owner DELETE, metadata-first deletion, post-delete zero-reference check, R2 HEAD confirmation and uncertain-status preservation remain intact.
