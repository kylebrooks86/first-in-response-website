### 1. Customer property archival now requires saved D1 verification

Previously the candidate-only `PATCH /api/customer-properties` parsed unrestricted `request.json()` then trusted a single `UPDATE ... RETURNING` ACK. A lost database acknowledgment after physical archival or a false-positive `RETURNING` could mislead the owner; a second deliberate request could report a false revision conflict despite a valid archived record.

- [Source commit `26cfcf27373d4cec59df80d2c9b806f64ef3b687`](https://github.com/kylebrooks86/first-in-response-website/commit/26cfcf27373d4cec59df80d2c9b806f64ef3b687) reuses the already-existing owner-only streamed strict UTF-8/JSON guard, 8,192 bytes before any D1 reads/writes. The original atomic `UPDATE customer_properties SET active=0,revision=revision+1 WHERE id=? AND customer_id=? AND active=1 AND revision=?` remains intact, and archive history/immutable triggers remain unchanged. **A separate exact-ID/customer D1 SELECT now must confirm `active=0` and `revision=expectedRevision+1`** before HTTP 200. Same revision replay or committed-but-lost ACK recovers the retained row without another update; an unconfirmed/fake positive ACK returns 503 `saveUncertain`, not success.
- [Native SQLite regression `75a11cd0fea9d090e2d8bdc35f45296c70c4af1a`](https://github.com/kylebrooks86/first-in-response-website/commit/75a11cd0fea9d090e2d8bdc35f45296c70c4af1a) extends the existing actual route/SQLite fixture with malformed/overlong JSON requests and **zero D1 activity**, saved archive revision/retained address, safe same-request replay, wrong-customer/stale-revision/unknown-field negatives, committed-but-lost DB write ACK, fabricated `RETURNING` response without data, and readback failure after a real commit followed by safe recovered retry.
- [Owner UI receipt verification `ae92189657ad1d8ca387f27bf57bd199f1f88f39`](https://github.com/kylebrooks86/first-in-response-website/commit/ae92189657ad1d8ca387f27bf57bd199f1f88f39) additionally demands the returned archive ID, customer, immutable address/unit, status and exact `+1` revision match the selected record before displaying confirmed success. The UI retains the existing manual read-only review action when uncertain.

**Flag boundary:** Customer-property management is **still candidate-only**, gated by existing `synthetic-only` flags. No DB migration, physical property feature activation or photo/job history modification was made.
