## Material owner customer-property reliability fix (candidate-only flag remains OFF in release)

The `POST /api/customer-properties` flow previously generated a **new random primary key per request** and trusted a single `INSERT...RETURNING` response. A lost D1/HTTP acknowledgement followed by a deliberate owner retry could duplicate an address record. It also buffered input unbounded.

- [`4db0d92b7c63f56d91ef2073c42dd9ee6f9ac781`](https://github.com/kylebrooks86/first-in-response-website/commit/4db0d92b7c63f56d91ef2073c42dd9ee6f9ac781) makes owner writes streamed/strict UTF-8 **8,192-byte** bounded before any D1 access, accepts an **optional owner-generated v4 `operationId`** as permanent property ID for retry-safe creation, refuses id reuse across customers/different addresses/archived records as 409, independently reads saved D1 physical row before returning HTTP success even after a claimed `INSERT` ACK, safely recovers a genuinely committed-but-lost acknowledgement as HTTP 200, refuses fabricated success with 503 `saveUncertain`, retains old clients that omit `operationId`, and distinguishes nonexistent customer 404. Atomic primary-key uniqueness already exists in the **previously reviewed candidate-only** property schema—**no SQL or schema modification**.
- [`39b0e367a476d859261f624cbb9c8d341b0f9004`](https://github.com/kylebrooks86/first-in-response-website/commit/39b0e367a476d859261f624cbb9c8d341b0f9004) changes the actual owner `CustomerProperties` UI to keep a **per-customer, exact draft-scoped UUID** across deliberate retry after an ambiguous HTTP result, verify returned row identity/address/active state, and reset that UUID only after confirmed saved response or switching customers/drafts.
