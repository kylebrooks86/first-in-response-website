# Customers offline repository boundary

2026-10-12 America/Chicago. Full Business App readiness remains **3/10 (30%)**.

The shared Customers screen currently reads contact details, estimates, invoices, notes, photos, messages and payments through a single `/api/customers` response. It also calculates job/payment figures from those collections. Connecting the contacts-only encrypted vault as a substitute for the entire response would misrepresent missing financial/job history. The new opt-in repository supplies contact reads and explicit local saves while marking job history connection-required. It is deliberately not imported by Dashboard or any app route yet.

`shared/lib/local-customer-repository.ts` consumes an explicitly provided encrypted vault. It exposes read, subscribe, unlock, save, lock and dispose. Locked/unavailable/loading/closed states return null contacts and pending counts instead of empty business data. Ready state returns detached contacts, retained operation count and save status. It never fetches APIs, seeds a vault, stores a phrase, restores data, migrates a schema, generates financial totals or reconciles server operations.

A successful save returns only after the existing encrypted transaction completes, and uses the current snapshot even when an idempotent retry returns an older operation receipt. Concurrent writes are refused. Failed writes require inspection rather than automatic retry or a promise that nothing committed. Vault locks immediately invalidate the repository and notify subscribers with cleared data. Read paths recheck synchronous cross-tab revocation. Generation checks after asynchronous work and after subscriber notifications prevent late plaintext from being returned if a callback locks the app. Subscriber exceptions/mutations cannot affect other subscribers or vault contents. Dispose revokes the shared vault session and clears listeners; callers must account for this explicit shared-vault lock behavior.
